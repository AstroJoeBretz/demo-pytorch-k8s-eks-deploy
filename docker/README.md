# PyTorch Toy Classifier — Step 1: Containerize It

A minimal but real PyTorch model served over HTTP with FastAPI, packaged
into a Docker image. This is step 1 of the Kubernetes/KServe learning
plan — before touching Kubernetes at all, get comfortable with what's
actually going to run inside a pod.

## What's here

```
model/                      (source of truth, at the project root)
  model.py                  model architecture (shared by train + inference)
  train.py                  trains on synthetic data, saves model_artifacts/model.pt
  inference.py              FastAPI server: /health and /predict
  model_artifacts/
    model.pt                trained weights (generated by train.py)
docker/
  Dockerfile                CPU image (multi-stage)
  Dockerfile.gpu            GPU variant using an nvidia/cuda base image
  Dockerfile.dockerignore   ignore rules for Dockerfile (Dockerfile.gpu.dockerignore for the GPU one)
  requirements.txt          pinned serving dependencies
```

The build context is the project root. The image copies `model.py`,
`inference.py` and `model_artifacts/` into `/app`; `train.py` is not
included.

## What's already verified

The Python code (model, training loop, FastAPI server) was actually run
and tested end-to-end:
- Training converges on synthetic data (100% train accuracy after 30
  epochs — it's a toy problem, so that's expected)
- `/health` returns `{"status": "ok", "model_loaded": true}`
- `/predict` returns real class probabilities for a valid request
- A malformed request (wrong number of features) is correctly rejected
  with a 422 and a clear validation error

**Not yet verified:** the Docker build itself. I don't have a Docker
daemon in this sandbox, so `Dockerfile` and `Dockerfile.gpu` follow
standard, well-tested patterns but you should build and run them
yourself to confirm — instructions below.

## Build and run it yourself

```bash
# from the project root (the build context must include model/ and docker/)
docker build -f docker/Dockerfile -t pytorch-toy-classifier .
docker run --rm -p 8000:8000 pytorch-toy-classifier
```

Then in another terminal:

```bash
curl http://localhost:8000/health

curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"features": [4.2, -3.1, 1.5, 2.2, -0.5, 3.1, 0.8, -2.9, 4.0, 1.1, -1.2, 3.5, 2.0, -0.8, 1.9, 2.5, -3.3, 0.4, 1.7, -2.1]}'
```

Check the image size — this is the number to watch:

```bash
docker images pytorch-toy-classifier
```

If you swap the Dockerfile to use plain `pip install torch` (no
`--index-url`), rebuild, and compare sizes, you'll see the difference
directly — expect several GB larger. That's not a hypothetical: while
building this, `pip install torch` in this sandbox pulled the default
CUDA-bundled Linux wheel and filled an entire 10GB disk before it
even got to installing torch itself. The CPU-only index isn't a
micro-optimization; for a CPU-serving image it's the difference between
a reasonably-sized container and one that barely fits on a node.

## Why the Dockerfile is built this way

**Multi-stage build.** Stage 1 (`builder`) has pip's build machinery and
whatever it downloads. Stage 2 (`runtime`) copies over *only* the
finished virtual environment and the application code — none of stage
1's layers exist in the final image. This is what makes a "slim" image
possible without hand-pruning files.

**CPU-only torch index.** Covered above — `download.pytorch.org/whl/cpu`
instead of the default PyPI wheel. Once you get to GPU node groups
in EKS, `Dockerfile.gpu` shows the inverse: there, you *want* the
CUDA-bundled wheel, so it uses the default index and an `nvidia/cuda`
base image instead of `python:slim`.

**Non-root user.** The final stage creates and switches to `appuser`
before `CMD` runs. Kubernetes Pod Security Standards (which you'll hit
in step 3) can enforce this — running as root is disallowed under the
"restricted" profile — so it's worth building the habit now rather than
retrofitting it later.

**`/health` doesn't touch the model.** This matters once Kubernetes is
running liveness/readiness probes against this endpoint every few
seconds (step 3) — it needs to be cheap and not itself become a source
of load or failure.
